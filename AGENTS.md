# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, Cursor, and similar tools) when working with code in this repository. It mirrors `CLAUDE.md` — keep both in sync when editing either one.

## What this is

"Plant Log Analyzer" (currently V29.76), a Thai-language browser tool for plant/machine monitoring engineers. Operators import Excel/CSV log sheets exported from plant SCADA/monitoring systems, and the tool auto-detects tag headers, normal-range limits, and per-row readings, flags out-of-range values, lets operators annotate abnormal readings, and exports a shift-summary "Infographic Report" as a JPG.

See `context.md` for the domain/business background (who uses this, glossary, and the rationale behind recent feature decisions) — this file covers the "how the code works" side.

**History note:** through V29.70 this was a single self-contained `index.html` file with zero build step. It was migrated to a Vite + ES Modules multi-file structure (see Architecture below) once the file passed ~3,500 lines and `EXCEL_WORKER` had accumulated 8 consecutive parsing-bug fixes (V29.63–V29.70) with no regression coverage — Vitest now guards that module. CDN-vendored libraries (Tailwind, lucide, xlsx, Chart.js, html2canvas, jsPDF) are untouched by the migration — they still load as plain `<script>` tags, just from `public/vendor/` instead of `vendor/`.

## Running / testing changes

- `npm install` once, then `npm run dev` for a Vite dev server with hot reload (open the printed `localhost` URL).
- `npm run build` produces the production bundle in `dist/` (this is what Cloudflare Workers deploys — see `wrangler.jsonc`).
- `npm test` runs the Vitest suite: `tests/excel-worker.test.js` (regression coverage for the V29.63–V29.70 parsing fixes) and `tests/excel-writeback.test.js` (covers `EXCEL_WRITEBACK`'s bridge-request logic with a mocked `fetch`, V29.74). `npm run test:watch` for watch mode.
- Automated tests cover `EXCEL_WORKER` parsing and `EXCEL_WRITEBACK`'s request-building/status-mapping logic only — the actual Excel-writing happens outside this repo's test reach, in `bridge/excel-bridge.ps1` via COM automation. Still verify UI changes manually: import a sample .xls/.xlsx/.csv log sheet through the "นำเข้าข้อมูล" (Import) tab and exercise the affected flow (import → dashboard flagging → annotate/report → infographic export). To verify the Excel write-back end-to-end, run `bridge/excel-bridge.ps1` (see `bridge/README.md`), keep the source file open in Excel, and confirm a saved Resolution Remark actually lands as a comment in that live workbook.
- Data persists client-side in IndexedDB (database `PlantLogAnalyzerEnterpriseDB`) — clearing site data/browser storage resets the app. Schema/store names are unchanged by the multi-file migration.
- Bump the version string in **three** places when making a notable fix, following the existing `V29.40`-style convention seen in commit history and in-code comments (e.g. `// V29.40 FIX: ...`): `index.html`'s `<title>`, the "Ultimate Edition (VXX.XX)" label near the bottom of the Manual view, and the small sparkles badge in the header (top-right, next to `page-title`) — this last one went stuck at "V29.85 Strict Numeric Core" for many versions (V29.41–V29.97) before anyone noticed, precisely because it wasn't on this list.

## Architecture

`index.html` now holds only markup, modals, CSS, and CDN `<script>` tags — one `<script type="module" src="/src/main.js"></script>` at the end wires up the app. All JS lives under `src/`, as plain object-literal namespaces (no framework), one per file, connected with ES `import`/`export`:

- **`src/modules/shared.js`** — cross-cutting helpers and constants used by most other modules: `escapeHtml`, `getTagId`, `parseNum`, date/time parsing helpers (`isValidDayMonth`, `excelSerialToDateStr`, `excelSerialToTime`), limit-resolution helpers (`resolveEffectiveLimits`, `formatLimitText`), `getMasterMap`/`getTagMap`, modal show/hide, IndexedDB store-name constants, zero-shield tolerance constants, `formatCountermeasureAction` (MPS manual text formatting), `BRIDGE_URL`/`fetchWithTimeout` (shared by every module that talks to the Local Bridge, 4s timeout), and `CANONICAL_TIMES` (`['03:00','09:00','15:00','21:00']`, the PI Datalink refresh rounds) with two functions built on it: `getCanonicalTimesStatus(records, now)` (V29.78 FEAT, latest-date + which of the 4 rounds are missing, time-gated so a premature/stale record for a round that hasn't clocked yet is never counted as "present" — V29.82 FIX) and `getDefaultTimeFilter(records, now)` (V29.105 FEAT, reuses the former to pick the most recent round that has actually occurred, as the Dashboard's default `timeFilter` instead of `'all'`).
- **`src/modules/smart-agent.js`** (`SMART_AGENT`) — generates Thai-language natural-language summaries/analysis text for abnormal readings and shift summaries (rule-based, not an external AI call). When a record's Tag No has a curated entry in `COUNTERMEASURE_DB`, it appends the manual's English recommended-action text after the generic Thai sentence; tags with no curated entry get the same output as before this feature existed.
- **`src/modules/countermeasure-db.js`** (`COUNTERMEASURE_DB`) — a flat array of `{tagNo, direction, equipmentName, factor, sourceDoc, sourcePage, pdfTagRef, action}` sourced from internal MPS process-deviation manuals. Deliberately small and hand-curated — most real Tag Nos won't have an entry, and that's expected (falls back silently).
- **`src/modules/countermeasure-agent.js`** (`COUNTERMEASURE_AGENT`) — looks up `COUNTERMEASURE_DB` (and user-added entries in `STATE`) keyed by `tagNo`+`direction`(+`machine`) for O(1) exact-match lookup, no fuzzy matching.
- **`src/modules/ui-renderer.js`** (`UI_RENDERER`) — tiny DOM helper (`createEl`, `initIcons` for lucide icons).
- **`src/modules/state.js`** (`STATE`) — the single source of truth (`STATE.data`: tags, masterTags, records, filters, selection). `STATE.set(key, value)` triggers `_recomputeFlags()` on `records`/`masterTags` changes (V29.78 PERF split from the older single `_deriveAbnormal`) and `_applyFilterSort()` (cheap filter/sort into `STATE.data.abnormalRecords`, reruns on `records`/`timeFilter`/`masterTags`/`viewFilter`), then notifies subscribers. `_recomputeFlags` itself is two passes: pass 1 computes `isAbnormal`/`isStandby` per record against min/max/exact limits (with the "zero shield" to suppress false positives near zero); pass 2 (V29.84 FEAT, flipped to opt-out in V29.92) computes `isStatDeviation` — enabled by default for every non-exact-value tag (opt-out per tag via `master.disableStatDeviation`, for tags that naturally swing widely e.g. batch processes) — a second detection criterion that flags a reading as abnormal-relative-to-itself (>3σ from a causal, leave-one-out rolling baseline of the tag's own last 120 samples, via `computeCausalStatDeviation` in `shared.js`) even when it's still within the hard min/max spec — built for tags whose official spec is far wider than their real operating band (e.g. a temperature tag with spec 220–262 that in practice never leaves 253–254; a drop to 238 signals sensor clogging, not a real out-of-spec event, and the hard-limit check alone would miss it). The same pass also computes `isStatTrendWarning` + `trendReason` (V29.92 FEAT, via `computeCausalStatTrendWarning` in `shared.js`, reusing the z-score stream `computeCausalStatDeviation` already produced) — a lighter early-warning tier below the >3σ alarm, firing on either 2-of-3 recent points beyond 2σ on the same side (`'PERSISTENT_2SIGMA'`) or 6 consecutive samples drifting monotonically in one direction (`'MONOTONIC_RUN_UP'`/`'MONOTONIC_RUN_DOWN'`). Severity ordering is enforced by construction: pass 2 only evaluates records that pass 1 already left at `isAbnormal===0 && !isStandby`, and `computeCausalStatTrendWarning` itself skips any sample already flagged `isStatDeviation===1` — so `isAbnormal` > `isStatDeviation` > `isStatTrendWarning` are mutually exclusive. `APP` subscribes once via `STATE.subscribe` and re-renders the active view based on the changed key (see `APP.render` in `src/modules/app/app-core.js`).
- **`src/modules/storage-engine.js`** (`STORAGE_ENGINE`) — thin IndexedDB wrapper (object stores: `Tags`, `Records`, `MasterTags`, `ImportHistory`, `UserCountermeasures`) for persisting imported data and operator annotations across reloads.
- **`src/modules/excel-worker.js`** (`EXCEL_WORKER`) — the CSV/Excel ingestion pipeline: `parseCSV` (quote-aware line splitter), `extractGlobalDate`/`normalizeYear` (parses dates from filename or sheet content, handles Buddhist-era years), `extractTime` (parses time from various formats including Excel serial fractions), and `processData` — the core row-classification state machine that walks each row of a sheet and, by matching header keywords (name/item/description, tag no, normal/limit), builds tag definitions and then reading rows keyed by column position. This is the most fragile/complex part of the codebase — log sheet layouts vary, so this uses heuristics (keyword matching, column-adjacency fallback for misaligned values, ignore-lists) rather than a fixed schema. **Has Vitest coverage** (`tests/excel-worker.test.js`) — add a test case here for any new parsing bug fix. Since V29.71, `processData` also computes each record's exact source-cell address (`sheetRow`/`sheetCol`/`cellRef`, via `colIdxToLetter`) for the Excel write-back feature below — this relies on `sheet_to_csv`'s CSV line/column index lining up exactly with the real Excel row/column (true today because `app-import.js` calls it with no blank-row/range trimming options; don't add any without re-checking this).
- **`src/modules/excel-writeback.js`** (`EXCEL_WRITEBACK`, V29.71, rearchitected V29.74) — syncs a saved "Resolution Remark (Action Taken)" back into the original Excel file as a native cell comment (the same right-click → "New Comment" an operator used to have to add by hand), closing the loop so Excel only ever receives data from the Web App. **V29.74 architecture change:** this module no longer reads/writes Excel bytes itself. Real-world testing (see `context.md`) proved that no free JS library (SheetJS, exceljs) can write these log sheets back out without corrupting them — the plant's log sheets contain live OSIsoft PI Datalink formulas, and every JS-library write path dropped `calcChain.xml`, forcing Excel to recalculate those formulas and show `#NAME?` everywhere even though the underlying data was fine; the SheetJS `.xls` (BIFF8) path was worse still — Excel refused to open the resulting file at all. Only genuine Excel (via COM automation) round-tripped these files with zero data loss. So `EXCEL_WRITEBACK` now just talks HTTP to a **Local Bridge** (`bridge/excel-bridge.ps1`, a PowerShell script the operator runs on their own machine) which drives the actual open Excel instance via COM. `buildWriteRemarkPayload` (pure, unit-tested) builds the request body; `syncRemarkToExcel` POSTs it to `http://localhost:5175/write-remark` and maps the response/network failure to a status string (`'ok'`/`'conflict'`/`'no-file-open'`/`'no-source-file'`/`'bridge-offline'`/`'error'`); `checkBridgeStatus` pings `/ping`. The bridge finds the target workbook by matching **filename** against the workbooks already open in the operator's running Excel instance (`record.sourceFileName`, set at import time in `app-import.js`) — not a filesystem path, since browsers never expose one — so the source file must be open in Excel for a sync to succeed. The conflict-detection rule (never overwrite a comment authored by someone other than the app) now lives in the PowerShell script, not JS.
- **`src/modules/excel-autoimport.js`** (`EXCEL_AUTOIMPORT`, V29.78) — the other direction from `EXCEL_WRITEBACK`: pulls new readings from the log sheet into the Web App automatically instead of the operator dragging the file into "นำเข้าข้อมูล" every time. `APP.pollAutoImport` (`app-core.js`, started once via `APP.startAutoImportPolling` in `init()`, then every `AUTOIMPORT_POLL_INTERVAL_MS` = 5 min) drives it as a fixed sequence each cycle: `autosaveSourceFile` → `rolloverDailyFileIfNeeded` → `getSourceFileInfo` (compare `lastWriteTimeUtc` against `LS_AUTOIMPORT_LAST_MTIME_KEY` in `localStorage`; skip the rest if unchanged) → `fetchSourceFile` (raw bytes, only when the mtime did change) → `APP.handleAutoImportedFile` (the V29.78 lightweight sibling of `handleFiles` in `app-import.js`) → `checkAndArchiveIfComplete`. **`autosaveSourceFile` (V29.102 FIX)** exists because the log sheet's live OSIsoft PI Datalink formulas recalculate and display new values on screen without ever writing them to disk until someone hits Ctrl+S — so before V29.102 the mtime never changed and a reading could sit fully computed in Excel but invisible to the Web App for hours; now the bridge saves the open workbook itself (if it has unsaved changes) as the very first step of every poll, before the mtime check even runs. `ensureFileOpen` (V29.99) is called both here and once fire-and-forget from `APP.init()` (`APP.ensureExcelFileOpen`) to reopen the log sheet if nobody has it open yet (e.g. a shift change where the previous operator's bridge session closed with them). `rolloverDailyFileIfNeeded` (V29.96) renames the file to today's date pattern and writes the new date into cell `W1` of sheet "BM 1", idempotently, once per calendar day. `LEGACY_UNKNOWN_FILENAME` is a one-time migration constant for records auto-imported before a CORS fix exposed the real filename.
- **`src/modules/excel-sync.js`** (`EXCEL_SYNC`, V29.85) — a third, independent use of the Local Bridge: keeps multiple operators who log into the same shared PC under **different Windows accounts** (and therefore different IndexedDB profiles — IndexedDB is scoped to the OS user, not to the app) looking at the same data. `pushSharedDb`/`pullSharedDb` POST/GET the entire `STORAGE_ENGINE.exportAll()` payload to `/save-shared-db` / `/load-shared-db`, which the bridge persists as one JSON file at a fixed path on the shared drive (`$SharedDbPath` in `excel-bridge.ps1`). `APP.pushSharedDb` (fire-and-forget, called from essentially every mutation site — see `grep -rn pushSharedDb src/modules/app`) drives the push side and flips the sidebar sync indicator (`APP.setSyncIndicator('synced'|'local')`, V29.85/87); the pull side runs once at `init()`, gated by `LS_SYNC_DIRTY_KEY` (never pull-and-overwrite local edits that failed to push in a prior session — see the comment block at the top of `init()` in `app-core.js`).
- **`bridge/excel-bridge.ps1`** (V29.74, most-recent notable change V29.110) — standalone PowerShell script, outside the Vite build (not imported by any JS, run directly by the operator, usually via Task Scheduler "At log on" or the Excel `HYPERLINK`/`bridge/start-bridge.bat` launcher — see `bridge/README.md`), that backs `EXCEL_WRITEBACK`/`EXCEL_AUTOIMPORT`/`EXCEL_SYNC` above. Listens on `http://localhost:5175/` and checks the request's `Origin` header against an allow-list (`$AllowedOrigins`) before doing anything. Routes: `GET /ping`; `POST /write-remark` (writes/deletes the Resolution Remark cell comment via COM — `Comment.Author` is read-only, so app-authored comments are produced by temporarily setting `Application.UserName` before `AddComment` and restoring it right after, which is how the conflict-detection check tells its own comments apart from a human's); `GET /source-file-info` + `GET /source-file` (mtime/size and raw bytes of the current log sheet in `$WatchFolder`, read with `FileShare.ReadWrite` so it still works while Excel has the file open); `POST /archive-source-file` (safety-copies it into `$ArchiveFolder\<Mmm yy>\`); `POST /rollover-daily-file` (V29.96, renames to today's date + writes `W1`, also clears the app's own old comments per V29.100); `POST /ensure-file-open` (V29.99, opens the workbook via COM if nobody has it open, without touching the rollover date logic); `POST /autosave-source-file` (V29.102, `$wb.Save()` if `$wb.Saved` is false); `POST /save-shared-db` + `GET /load-shared-db` (V29.85, atomic write/read of the shared-db JSON snapshot). Every route that resolves "the" log sheet file goes through `Resolve-SourceFile`, which refuses to guess if more than one non-`(master)` file is sitting in `$WatchFolder` (returns an error instead of picking one), and `Test-FileLooksLikeMasterTemplate` (V29.101) flags the case where a file's *name* was rolled over correctly but its *contents* are still byte-identical to the `(master)` template (something external overwrote it after rollover). **V29.106 FIX:** `$listener.Start()` is now wrapped in try/catch — a second bridge instance colliding with an already-running one on port 5175 used to crash with a raw, scary .NET exception; now it prints a plain-Thai "another Bridge is already running, just close this window" message instead. **V29.110 FIX:** `Find-OrOpenWorkbook` (used by `/ensure-file-open` and `/rollover-daily-file`) used to only check for an already-open copy via `$excel.Workbooks` on its own COM session — `GetActiveObject` is scoped per Windows logon session, so on the shared PC (multiple operators, different Windows accounts, see `EXCEL_SYNC` above) it couldn't see a file already locked open by a *different* session's Excel, and would call `Workbooks.Open()` again with `Notify` left at its COM default (`True`), triggering Excel's native "already open" popup and leaving the new copy read-only. It now calls `Test-FileLockedByOtherSession` first, which checks for Excel's `~$<filename>` lock-owner file on disk (visible across sessions, unlike COM) before attempting to open — if locked, it returns `{status:'locked-by-other-session'}` instead of opening, and `Workbooks.Open()` itself now also passes `Notify:=$false` as a backstop against the remaining race window. See `bridge/README.md` for setup/Task Scheduler autostart instructions, and the "เปิด Bridge จากปุ่มในหน้า Web App" section for the `plantlogbridge://` custom URI protocol (V29.103, registered via `bridge/register-protocol.reg`/removed via `bridge/unregister-protocol.reg`, both under `HKEY_CURRENT_USER` so no admin rights are needed) that lets the sidebar "เปิด Excel Bridge" button (visible only while the sync indicator reads "LOCAL MODE") launch `start-bridge.bat` directly from the browser — `APP.retryConnectAfterOpenBridge` (`app-core.js`, V29.104, hardened V29.106) checks whether the bridge is already reachable *before* firing that protocol link, specifically to avoid the V29.106 double-instance scenario, then polls every 1s (up to 15s) until the bridge answers and immediately runs `pushSharedDb` + `pollAutoImport` — no manual page refresh needed.
- **`src/modules/app/`** (`APP` — a single shared object assembled across files via `Object.assign(APP, {...})`, so `APP.xxx()` calls work identically regardless of which file defines them):
  - `app.js` — declares the empty `APP` object; every other file in this folder extends it.
  - `app-core.js` — `init`, `loadLocalData`, `bindEvents`, `render` (dispatch on `STATE` changes), `backupData`/`restoreData`, plus the Local Bridge orchestration: `pollAutoImport`/`startAutoImportPolling` (see `EXCEL_AUTOIMPORT` above), `pushSharedDb`/`setSyncIndicator` (see `EXCEL_SYNC` above), and `retryConnectAfterOpenBridge` (see `bridge/excel-bridge.ps1` above).
  - `app-dashboard.js` — dashboard card rendering, auto-select-critical, report-selection toggling, backup-reminder banner.
  - `app-import.js` — import-history rendering, file-drop/upload handling (`handleFiles`, drives `EXCEL_WORKER`).
  - `app-tags.js` — read-only Tag Database table (`view-tags`).
  - `app-master.js` — Tag Master (limits override) table and edit modal (`view-master`).
  - `app-countermeasure.js` — user-added Countermeasure entries table and edit modal (`view-countermeasure`).
  - `app-modal.js` — the abnormal-record annotation modal (`openActionModal`/`saveAction`/`triggerSmartAssist`).
  - `app-chart.js` — the Chart.js trend chart (`renderChart`) shown inside the annotation modal.
  - `app-report.js` — the shift Infographic Report (`openReportModal` → `updateInfographicLive` → `exportInfographicImage`, which rasterizes `#infographic-container` via `html2canvas` and triggers a JPG download). Since V29.76, `renderInfographicRecords` renders the selected records as either a card grid or a `<table>` depending on `setInfographicLayout('card'|'table')` (toggle buttons in the modal) — both branches build off the same per-record data via `buildInfographicCardHTML`/`buildInfographicTableRowHTML`, and whichever layout is active at export time is what `html2canvas` rasterizes.
- **`src/main.js`** — imports `app.js` plus every `app-*.js` file (for their `Object.assign` side effects), then calls `APP.init()` on `DOMContentLoaded`. There are no inline `onclick`/`onchange` HTML attributes anywhere in this codebase — all event wiring goes through `bindEvents()`/`addEventListener` or JS `.onclick =` property assignment inside `APP` methods, so nothing needs `window.*` exposure.

### Data model essentials

- A **tag** is a monitored point, identified by `getTagId(r) = ${machine}_${tagNo}_${paramType}` (paramType is PV/MV/SV/etc). Tags carry `min`/`max`/`exactNum` limits parsed from the sheet's "Normal"/"Limit" row.
- **`masterTags`** are operator-curated overrides of a tag's limits (edited in the "Master" tab) that take precedence over the per-import `tags` limits — see the override logic in `STATE._deriveAbnormal`. Master overrides live in their own IndexedDB store (`MasterTags`) and are never cleared by re-importing or by the "ล้างฐานข้อมูล" (Clear Database) button — only `Records` gets cleared by that button; `Tags` and `MasterTags` persist so limits/overrides don't need to be re-entered every shift.
- A **record** is one reading (one tag, one timestamp). Records get annotated in place with `isAbnormal`, `isStandby`, `remark`, `actionStatus` ('new'/'acknowledged').
- Values within ~0.1 of zero (or near zero relative to the limit) are treated as instrument "standby" and suppressed from abnormal flagging (the "zero shield", toggleable per-tag via `master.disableZeroShield`) — this exists to avoid false alarms from idle/offline instruments. For instruments whose idle baseline isn't near zero (e.g. a vibration sensor that reads ~13 while its equipment is parked), `master.forceStandby` lets an operator force a tag to always read as standby regardless of value.
- There is no cap on how many abnormal records can be selected for the Infographic Report (`STATE.data.selectedForReport`) — operators can select individual rows, use the "คัดเลือกอัตโนมัติ" (Top N by severity) dropdown, or "เลือกทั้งหมด" to select everything currently visible under the active filter.

## Working conventions (from this repo's history)

- All UI copy is Thai; keep new user-facing strings in Thai consistent with the surrounding tone.
- All external libraries (Tailwind, lucide icons, SheetJS `xlsx`, Chart.js, html2canvas, jsPDF) are loaded from `/vendor/*.js` in `<head>` as plain `<script>` tags — vendored copies committed to the repo at `public/vendor/` (Vite copies `public/` verbatim into `dist/`; not a CDN, and not npm-managed) so the app has zero network dependency once served. They are deliberately **not** converted to npm imports — modules that use them (`XLSX`, `Chart`, `html2canvas`, `jspdf`, `lucide`) reference the global via a `/* global ... */` comment. Google Fonts (`index.html:8-10`) is the one deliberate CDN exception, still loaded from `fonts.googleapis.com` — non-critical, degrades gracefully to a system font if offline. To update a vendored library, re-download it from its original CDN URL (see git history / `public/vendor/` filenames) and overwrite the file in place.
- User-supplied strings that reach the DOM must go through `escapeHtml` (an XSS fix landed in this repo's early history — don't regress it).
- Past fixes in this repo have centered on: tag-ID collisions across machines/sheets (always include `machine` in identity), date/time parsing edge cases in imported sheets, and text clipping in the exported Infographic JPG — when touching the infographic layout, verify the exported image (not just the on-screen preview), since html2canvas rendering can diverge from live CSS.
- `src/modules/shared.js` and `src/modules/state.js` import from each other (`getMasterMap`/`getTagMap` in `shared.js` call `STATE.get(...)`; `STATE._recomputeFlags` calls `getMasterMap`/`getTagMap`, and `computeCausalStatDeviation`, also in `shared.js`, feeds back into it). This is a deliberate circular ES import — safe here because both sides only touch the other's binding inside function bodies invoked later, never at module-evaluation time. Don't "fix" this by inlining or restructuring unless you're solving an actual problem it causes.
- `src/modules/app/app.js` exports a single empty `APP` object; every other `app-*.js` file does `Object.assign(APP, { methodName: ... })` as a module-level side effect. `src/main.js` imports every `app-*.js` file (for that side effect) before calling `APP.init()`, so by the time any method runs, `APP` is fully assembled — a method in one file (e.g. `app-modal.js`) can freely call `APP.renderChart` (defined in `app-chart.js`) without an explicit import of that method, only `import { APP } from './app.js'`. When adding a new `APP` method, add it to whichever `app-*.js` file matches its feature area (or create a new one) and it becomes available the same way; **don't** add a new import path just to call a sibling `APP.*` method.
- `wrangler.jsonc`'s `name` (`monitor-log-sheet-boardman`) must never change — the deployed URL is embedded in the plant's Excel log sheet via a `HYPERLINK` formula that operators click to open the app (see `HANDOFF.md`). `assets.directory` points at `./dist` (the Vite build output), not the repo root.

1. Session ใหม่ → เรียก `sa-explore` สำรวจโค้ดที่เกี่ยวข้องก่อน
2. Plan Mode (Opus) → วางแผน
3. Accept Edits (Sonnet) → ลงมือแก้
4. เรียก `sa-code-reviewer` ก่อน commit
5. ถ้าเจอ Critical issue → เรียก `sa-debugger` แก้ต่อ
6. เรียก `sa-git-manager` เพื่อ commit/push/PR อย่างปลอดภัย
