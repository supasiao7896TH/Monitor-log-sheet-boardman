# context.md

Domain and business background for this repository. `CLAUDE.md`/`AGENTS.md` cover how the code works; this file covers why it works that way.

## Who this is for

A single-operator (or small-team) tool used by plant/machine monitoring engineers at an industrial site to process shift log sheets — Excel/CSV exports from a plant's SCADA or monitoring system listing instrument readings (PV/MV/SV) taken at intervals throughout a shift. The primary user works in Thai and reviews readings against normal operating ranges to catch abnormal parameters, annotate them with corrective-action remarks, and hand a summary to the next shift.

## Glossary

- **Tag / Tag No.** — an instrument tag number, e.g. `VI-2401A`, `FI-2407`, `TI-2405`. Globally unique within the plant by convention.
- **Machine** — the equipment/sheet grouping a tag belongs to, e.g. `PM-401A`, `PM-401B`. Combined with tag number and param type to form a tag's identity (`machine_tagNo_paramType`) so the same tag number reused on different equipment doesn't collide.
- **PV / MV / SV** — Process Value / Measured Value / Set Value — the parameter type read alongside a tag number.
- **Norm / Limit** — the acceptable operating range for a tag (min/max, or an exact required value), normally parsed from a "Normal"/"Limit" row in the imported sheet.
- **Standby** — an instrument or piece of equipment that is not currently running. Its reading is often near-zero, but not always (see forced Standby below) — a Standby reading should not be reported as an abnormal alarm.
- **Master override** — an operator-entered correction to a tag's limits/behavior (via the "Master" tab), used when the Excel-derived data is wrong, missing, or needs special handling.
- **Infographic Report** — the exported JPG shift-handover summary built from a hand-picked set of abnormal (or otherwise selected) parameters.

## Notable feature decisions (most recent first)

- **Remove the `$wb.Saved` gate from the Bridge's autosave route — it was never actually verified to work with PI Datalink (V29.107).** The operator reported that even after V29.102 (below) shipped, they still had to manually hit Ctrl+S in Excel for readings to reach the Web App — the exact symptom V29.102 was supposed to eliminate. Investigation traced it to an unverified assumption baked into `Handle-AutosaveSourceFile`: it checked `if ($wb.Saved) { skip .Save() }`, on the theory that Excel sets `.Saved` to `$false` itself whenever a PI Datalink external-data-link refresh changes a displayed value, the same way a manual cell edit would. Nothing in this repo's history ever tested that theory directly — the V29.102 HANDOFF.md entry itself has no "tested" section, unlike neighboring entries — and it turned out to be wrong in practice: an external-data refresh doesn't reliably trip the same COM dirty-flag a manual edit does, so `.Saved` stayed `$true` even after PI pushed a new value to screen, the gate silently skipped `.Save()` every cycle, the on-disk mtime never moved, and `pollAutoImport`'s mtime comparison never had anything to pick up. The fix removes the gate entirely — `$wb.Save()` now runs unconditionally on every 5-minute poll — trading a few no-op disk writes for not depending on a COM property that's already been shown to lie about the one case that mattered most. Also closed a related diagnostic gap: `pollAutoImport` used to deliberately not log an autosave status of `'no-file-open'`, on the assumption it was a normal, expected state; that same silent-whitelisting is exactly what let this bug hide for as long as it did, so it's now logged (and surfaced as a Dashboard banner) like any other non-`'ok'` status.
- **Stop the "เปิด Excel Bridge" button from launching a duplicate Bridge instance (V29.106).** The button (below) always fired the `plantlogbridge://` protocol on click, even when a Bridge was already running but the sync indicator hadn't caught up yet (a real timing gap right after page load, before the first `pushSharedDb`/`pullSharedDb` resolves) — the operator hit this in practice: a second `excel-bridge.ps1` spawned, collided with the first on port 5175, `$listener.Start()` threw an unhandled exception (no try/catch existed), and the operator was left staring at a black terminal window that "wasn't closing itself like usual," showing a scary raw .NET stack trace above `start-bridge.bat`'s normal "press any key to close" prompt. Fixed on both sides: the click handler now checks `getSourceFileInfo()` first and only navigates to the protocol link if the Bridge is truly unreachable; `excel-bridge.ps1` also wraps `$listener.Start()` in try/catch so any *other* source of a port collision (e.g. the Excel `HYPERLINK` and Task Scheduler racing on login) now prints a plain-Thai "another Bridge is already running, just close this window" message instead of the exception dump — belt-and-suspenders, since the client-side check can't cover every path that launches the script.
- **Default the Dashboard's parameter list to the current time round instead of "All Time" (V29.105).** The operator asked, essentially, why they had to manually filter down to the current shift's data every time they opened the app — with "All Time" as the default, months of history sat mixed in with whatever just came in. `getDefaultTimeFilter` (`shared.js`) reuses `getCanonicalTimesStatus`'s existing time-gating (so a premature/stale record for a round that hasn't actually occurred yet still isn't picked, same protection as the V29.82 fix) to pick the most recent of the 4 daily rounds that has genuinely happened, and that becomes the `timeFilter` on fresh page load, after an import, and after a restore — deliberately *not* re-applied on every 5-minute auto-import poll or other `loadLocalData()` call, so it never yanks a specific round the operator picked manually mid-shift back to "now."
- **Auto-sync the sidebar indicator after clicking "Open Bridge," without a page reload (V29.104).** Clicking the button (below) only fired the OS-level protocol; the page had no way to know the Bridge had actually come up, so the operator had to manually refresh to see "SYNCED." Added a short client-side poll (`APP.retryConnectAfterOpenBridge`, every 1s for up to 15s — the Bridge answered `/ping` within ~2-3s in testing) that runs `pushSharedDb` + `pollAutoImport` the moment the Bridge responds.
- **Let the Web App open the Local Bridge directly, via a custom URI protocol (V29.103).** The operator already had a one-click `HYPERLINK()` in the Excel log sheet to launch `bridge/start-bridge.bat`, and asked for the same convenience from the Web App page itself. A plain `<a>`/JS click can't launch a local `.bat`/`.exe` — that's exactly the browser sandbox limitation `EXCEL_WRITEBACK` (`context.md`, V29.74 entry) already had to route around via the Bridge in the first place — so the only way to get a real "click a web button, a local program launches" experience is a registered custom URI scheme. Chose `plantlogbridge://`, registered under `HKEY_CURRENT_USER\Software\Classes` (not `HKEY_CLASSES_ROOT`) specifically so importing `bridge/register-protocol.reg` never needs Administrator rights and stays scoped per Windows account — consistent with the "Specific user" Task Scheduler pattern already documented in `bridge/README.md` for the same shared-PC constraint. A sidebar button (`#btn-open-bridge`, visible only while the sync indicator reads "LOCAL MODE") links to it; the browser shows a one-time "open this app?" confirmation the operator can set to remember.
- **Auto-save the log sheet from the Bridge before every auto-import poll (V29.102).** The operator reported that a reading due at a fixed time (e.g. 9:00) wasn't appearing in the Web App until they manually hit Ctrl+S in Excel. Root cause: the log sheet's live OSIsoft PI Datalink formulas recalculate and display the new value on screen the moment PI refreshes, but Excel never writes that to the file on disk until an actual save happens — and `pollAutoImport` (V29.78, below) only ever checked the file's on-disk `LastWriteTimeUtc`, so a fully-computed reading could sit correct on screen but invisible to the Web App for hours. Rather than ask the operator to remember to save on a schedule, the Bridge now saves the open workbook itself (`$wb.Save()`, only if `$wb.Saved` is false, to avoid needless disk writes) as the very first step of every 5-minute poll cycle, before the mtime check even runs.
- **Auto-import/auto-archive the log sheet via the Local Bridge, instead of manual drag-and-drop (V29.78, hardened through V29.101).** The original "นำเข้าข้อมูล" flow required an operator to manually drag the log sheet into the Web App every time new readings landed — easy to forget, and the whole point of automating data collection from PI Datalink was undermined by a manual step still sitting in the middle. `EXCEL_AUTOIMPORT` polls the Bridge every 5 minutes for the current log sheet's mtime/bytes and imports automatically when it changes, and also handles safety-archiving a copy once a day's 4 rounds are complete and, later, the daily filename/date-cell rollover (V29.96) that used to be a manual morning task too. This shipped with several real production bugs that only surfaced under actual shift conditions rather than testing: auto-imported records initially got a placeholder `sourceFileName` instead of the real one because the CORS setup hid the `Content-Disposition` header the code was relying on (V29.79); `Resolve-SourceFile`'s "exactly one non-`(master)` file" rule didn't know to ignore Excel's own `~$...` lock file, so it saw "2 candidate files" and refused to import for as long as the log sheet was open in Excel — i.e. almost always in real use (V29.81); a re-import (whether from this poll or a manual drag-drop) rebuilt every record from the sheet with `remark: ''` hardcoded, silently wiping a just-saved Resolution Remark the moment the Bridge's own `$wb.Save()` (for a remark sync) changed the mtime and triggered the next poll — fixed by carrying the prior `remark`/`actionStatus` forward on re-import (V29.83); and `getCanonicalTimesStatus` could report a round complete before it had actually occurred, because a stale/placeholder value already sitting in that round's cell (before PI recalculated it) looked identical to a real reading (V29.82, the fix this function's time-gating still relies on today — see the `getDefaultTimeFilter`, V29.105, entry above). Later hardening: `ensure-file-open` (V29.99) reopens the workbook automatically if a shift change leaves nobody with it open, and `Test-FileLooksLikeMasterTemplate` (V29.101) catches the case where rollover renamed the file correctly but something external overwrote its *contents* back to the blank `(master)` template afterward — both surfaced as visible Dashboard warnings rather than failing silently.
- **Keep multiple shared-PC operators (different Windows accounts, different IndexedDB) looking at the same data (V29.85).** The Office PC is used by several shift operators who each log into their own separate Windows account — since IndexedDB is scoped to the OS account, not the app, whoever logged in next saw a completely empty Dashboard, with no visibility into readings or remarks a prior operator had just entered. Rather than introduce real backend infrastructure, `EXCEL_SYNC` piggybacks on the Local Bridge already running on that PC: `STORAGE_ENGINE.exportAll()`'s full snapshot is pushed to a fixed JSON file on the shared drive after every mutation (fire-and-forget) and pulled once at `init()`. Two guards were needed to keep this safe: `init()` never pushes on its own (only a real local mutation triggers a push, so an empty/fresh IndexedDB can never overwrite the shared file), and a `localStorage` dirty-flag tracks any push that failed (e.g. Bridge briefly offline) so a subsequent `init()` retries that push *before* allowing a pull — otherwise a reload could silently discard an edit that never made it to the shared file.
- **Auto-enable Statistical Deviation for every tag instead of opt-in, add a lighter "Trend Warning" tier below it (V29.92).** The opt-in design from V29.84 (below) meant that, in practice, no tag ever had it turned on — the operator would have had to remember to visit Tag Master and tick a box per tag before the feature did anything. Flipped to opt-out (`master.disableStatDeviation`, mirroring the existing `disableZeroShield` pattern) so every non-exact-value tag gets the >3σ check by default. Also added a second, earlier-warning tier (`isStatTrendWarning`) below the >3σ alarm, reusing the same z-score stream: 2-of-3 recent points beyond 2σ on the same side, or 6 consecutive samples drifting monotonically in one direction — catching a reading on its way out of control, not just once it's already there. Severity is enforced by construction so the three tiers (`isAbnormal` > `isStatDeviation` > `isStatTrendWarning`) stay mutually exclusive.
- **Turn the Dashboard's summary cards into click-to-filter controls, and default to "Abnormalities" only (V29.93/94).** After the Trend Warning tier (above) added a third category to the "รายการพารามิเตอร์" list, the operator found all three types blended together under one filter hard to scan, and separately felt the previous "abnormal" default (all three types combined) buried the readings that actually violate a hard limit under the two softer statistical tiers. Rather than add new UI on top of the four summary cards already sitting above the list, made the existing cards themselves clickable filters (click again to clear back to the default), and changed that default from "abnormal" (all three) to the new `'hard-abnormal'` (real limit violations only) — the two statistical tiers are still one click away on their own cards, just no longer competing for attention by default.
- **Decision: don't add a browser-facing "settings" UI for the Local Bridge's folder paths.** Raised as a forward-looking question (not an active migration) — if the Web App ever needs to be used from a PC other than the one currently hosting the Local Bridge, would a settings button (e.g. "save Excel files to this folder") be needed? No: the Web App itself is already location-independent (a Cloudflare Workers-hosted site, opens from any browser on any PC) — the only machine-bound piece is the Local Bridge (`bridge/excel-bridge.ps1`), tied to one PC because it drives Excel via COM automation and talks to the browser over `localhost:5175`. Its folder-path variables (`$WatchFolder`, `$ArchiveFolder`, `$SharedDbPath`, `$AllowedOrigins`) are deliberately hardcoded in the script and never accepted from the browser (see the comment at `bridge/excel-bridge.ps1:36-48`) — accepting a path from the browser would let anything that can reach the local HTTP endpoint direct the bridge to read/write arbitrary files on that machine, undermining the exact protection that hardcoding was meant to provide. If the Bridge does need to move to a different machine in the future, the correct/intended path is still to edit those variables directly in `excel-bridge.ps1` and re-register the Task Scheduler entry on the new machine (already documented in `bridge/README.md` as a one-time admin/setup step) — not a runtime, operator-facing setting.
- **Card/Table layout toggle for the Infographic Report (V29.76).** The Infographic Report's card-grid layout (2 columns, one large card per abnormal Tag) was designed to look good shared as a JPG to management over LINE, but with 10+ abnormal Tags in a shift it got very tall and slow to scan — the user asked whether a table would be "easier." Rather than replace the card layout outright (it's the one specifically designed for the executive-facing "Infographic"/visual-impact use case — a plain data table would undercut that), added a toggle in the Live Preview header so both are available: Card (unchanged) for sharing, Table (new, 6 columns: Tag/Description/Norm/Value/Time/Action Remark, red-tinted rows for abnormal readings) for a denser view. Both layouts render from the same per-record data (`APP.buildInfographicCardHTML` / `APP.buildInfographicTableRowHTML` in `src/modules/app/app-report.js`), and whichever is on screen when "Save as Image/PDF" is clicked is what gets rasterized, since export always captures `#infographic-container` as-is via `html2canvas` regardless of layout.
- **Fix silent Excel-sync failure when a cell already had a Threaded Comment (V29.75).** An operator reported a specific Tag (`LI-2601`) consistently failed to sync its Resolution Remark to Excel while every other tag succeeded, surfacing only a generic "Sync กลับ Excel ไม่สำเร็จ" message client-side. The actual bridge response (captured via the browser's Network tab) was an opaque COM error, `Exception from HRESULT: 0x800A03EC`, common to many different Excel Interop failures and not diagnostic on its own. Root-caused by temporarily wrapping each risky step in `Handle-WriteRemark` (`bridge/excel-bridge.ps1`) in its own try/catch, which pinpointed the failure to `Range.AddComment()` specifically. Cause: Excel has had two independent comment systems since 2019/365 — legacy Notes (`Range.Comment`, what this app writes) and Threaded Comments (`Range.CommentThreaded`, what the "New Comment" button creates by default in modern Excel). The bridge's conflict check only read `.Comment`, so a cell an operator had already commented on directly in Excel (via the modern threaded UI, before this sync feature existed) looked empty to the bridge — it then tried `AddComment()` on top of the existing thread, which Excel's COM layer rejects with the generic HRESULT above. Fixed by also checking `.CommentThreaded` and treating any hit as a `conflict` (same non-destructive behavior as an existing legacy comment) instead of attempting the write. Since the app itself only ever writes legacy Notes, any Threaded Comment found is guaranteed to be human-authored, so no author check is needed on that branch (unlike the legacy-comment conflict check, which does compare `Author`).
- **Multi-user shared-PC deployment pattern for the Local Bridge.** The Office PC running this app is shared across shift operators who each log in with their own separate Windows account (not a single shared login), which broke two assumptions the original Local Bridge setup (V29.74, below) made: (1) the repo lived under the setup operator's personal profile (`C:\Users\<name>\...`), unreadable to any other account under normal NTFS permissions; (2) the documented Task Scheduler "At log on" trigger was scoped to one specific account, so the bridge never auto-started for anyone else who logged in. Moving the repo to a local fixed drive outside any profile (not a mapped network drive — those are just as login-dependent as `C:\Users\...`, typically assigned per-account by a login script) with `BUILTIN\Users` granted read+execute (`icacls ... /grant "Users:(OI)(CI)RX" /T`) solved the first problem. The second needed more than expected: Task Scheduler's "Any user" logon trigger (a `-GroupId` principal) requires local Administrator rights to register, full stop, regardless of who runs the command — confirmed by `Register-ScheduledTask` failing with `Access is denied` under a non-admin domain account. Without admin rights available, the practical fallback is a hybrid: a `-UserId`-scoped ("Specific user") task for the one account that has setup access (registers fine without admin rights, since you're only ever granting yourself a task), plus a one-click manual path for every other operator via `bridge/start-bridge.bat` (a thin wrapper so a plain Excel `HYPERLINK()` formula can launch it directly — Windows won't execute a `.ps1` on open/double-click by default, but will run a `.bat`/`.cmd`) pasted into the log sheet itself, mirroring the existing HYPERLINK-to-the-web-app pattern already in use. See `bridge/README.md` for both setups side by side.
- **Replace JS-library Excel write-back with a Local Bridge driving real Excel via COM (V29.74).** The V29.73 fix (below) solved the "wrong container format" symptom but the operator reported the exported file still didn't look right — missing the company logo, header background colors, and correct row heights. Investigating further with real production files (including `P1-F-2002-22 (09-08-26) (Digital).xlsm`, which carries live OSIsoft PI Datalink formulas — `_xll.PITimeDat(...)` — in every reading cell) turned up a much bigger problem than cosmetics: **every write path tested through a free JS library actively corrupted the file's data display.** SheetJS dropped `xl/calcChain.xml` on write regardless of target format, which makes Excel force-recalculate every formula on open — with the PI Datalink add-in not guaranteed to resolve instantly, this turned every PI-linked reading into `#NAME?` even though the correct cached value was still sitting in the file. exceljs (tried as a higher-fidelity alternative — it does preserve colors/fonts/row-heights/merges/embedded-images perfectly, verified via a round-trip that Excel rendered pixel-identical to the original) hit the exact same `#NAME?` problem, and can't touch `.xls`/VBA macros at all. Hand-patching a fresh `calcChain.xml` back into a SheetJS-written file (copying the original's, since no formula cells were touched) was tried as a middle ground — it made Excel refuse to open the file entirely. And the V29.73 fix itself (`.xls` → `bookType:'biff8'`) turned out to still produce a file real Excel's own `Workbooks.Open` rejects outright ("Office has detected a problem with this file"), independent of Mark-of-the-Web/Protected View — confirmed by testing via PowerShell COM automation directly, bypassing the browser download flow entirely. The one approach that round-tripped a real PI-formula-laden log sheet with **zero** loss (colors, logo, macros, row heights, and — critically — correct PI values with no forced recalculation) was letting genuine Excel do the write, via `Range.AddComment` COM automation. Since a browser can't drive COM directly, `src/modules/excel-writeback.js` was rearchitected to talk HTTP to a new **Local Bridge** (`bridge/excel-bridge.ps1`) that operators run on their own machine; it finds the target workbook among Excel's already-open windows by filename (a real filesystem path was never available to the browser side anyway) and lets Excel itself add/replace/delete the comment. This also let the app drop the Chrome/Edge-only File System Access API path (`FileSystemFileHandle`, `showOpenFilePicker`, the "นำเข้าและเชื่อมต่อไฟล์" button) and the SheetJS-based "Export Updated Excel" download fallback entirely — both are superseded by the bridge, which works the same way in any browser and doesn't silently produce a corrupted/mismatched file the way the old fallback risked doing.
- **Fix `.xls` write-back producing OOXML bytes disguised as `.xls` (V29.73).** An operator reported that a downloaded "Export Updated Excel" file, when the source log sheet was a legacy `.xls` (Excel 97-2003 binary/BIFF8), "didn't look like the original" — confirmed by comparing file magic bytes: the original was a genuine `Composite Document File V2` (BIFF8) and the export was actually `Microsoft Excel 2007+` (OOXML/zip) bytes just saved under the same `.xls` filename/extension. Root cause: `pickBookType()` in `src/modules/excel-writeback.js` only special-cased `.xlsm`, defaulting everything else (including `.xls`) to `bookType:'xlsx'`. Fixed by mapping `.xls` → `bookType:'biff8'` explicitly (the vendored SheetJS build genuinely supports writing real BIFF8, this wasn't a library limitation). Same bug affected the auto-sync-to-disk path (`syncRemarkToExcel`), which was silently overwriting `.xls` source files on disk with mismatched-format bytes on every remark save — a more serious variant since it corrupts the user's original file, not just a new export. Known residual limitation (not fixed by this change, a SheetJS community-edition constraint): embedded pictures/shapes/charts in a source file are not preserved by any write path, regardless of bookType.
- **Auto-sync Resolution Remark → Excel native cell comment (V29.71).** Feedback from operators: after annotating an abnormal reading in the Web App, they were still going back into the original Excel log sheet, finding the same cell, and right-clicking → "New Comment" to retype the same reasoning by hand — pure duplicate work, and it meant the Excel file could drift out of sync with what the Web App said. Confirmed by inspecting a real production sample (`P1F200222_100826_Digital.xlsm`) that "New Comment" here means Excel's native legacy cell comment (VML-based, `xl/comments*.xml`), attached directly to the abnormal reading's own cell — not a separate spreadsheet column. Now, saving a Resolution Remark writes that comment automatically: when the operator connects the file via the new "นำเข้าและเชื่อมต่อไฟล์" import button (File System Access API — Chrome/Edge only), the app writes straight back to the same file on disk on every save; on any other browser, or if permission is lost, an "Export Updated Excel" button regenerates a fresh copy with every remark applied. A comment authored by anyone other than the app itself is never silently overwritten (surfaced as a "conflict" status instead), so a human's hand-typed comment in Excel can't be destroyed by a later remark save. `.xlsm` macros round-trip untouched. See `src/modules/excel-writeback.js`.
- **Offline-vendored libraries, import audit trail, backup reminder, recurring-abnormality badge (V29.51).** The user confirmed the app is normally opened by double-clicking `index.html` directly (`file://`), not through any server — this rules out a true installable PWA (Service Workers refuse to register on a `file:` origin), so "make it work offline" was scoped down to vendoring the 6 CDN `<script>` libraries (Tailwind, lucide, SheetJS `xlsx`, Chart.js, html2canvas, jsPDF) as local files in `vendor/` instead, giving zero network dependency without needing a server. Google Fonts stays on CDN deliberately (non-critical, degrades gracefully). The other three: (1) an `ImportHistory` IndexedDB store logging every imported file (name, size, tags/records added, success/error) since the on-screen process log was transient and wiped on the next import; (2) a dismissible Dashboard banner nudging operators to back up if they never have, or it's been 3+ days, since Backup/Restore (below) is opt-in and easy to forget; (3) a "recurring" badge on abnormal Dashboard cards when a tag has been abnormal 3+ times all-time, to surface chronic issues instead of one-off blips, built on the same per-tag grouping the annotation-history feature already introduced.
- **Backup/Restore, Dashboard search, per-tag annotation history, PDF export (V29.50).** Four gaps identified as the highest-risk/highest-friction missing features and closed together: (1) a JSON export/import of the entire IndexedDB (Tags/Records/MasterTags) since all data previously lived only in one browser's local storage with no recovery path if it was cleared; (2) a search box on the Dashboard's abnormal-record list, matching the search boxes already present on the Tags and Master tabs; (3) a "Past Actions" panel in the annotation modal showing a tag's last 5 prior remarks, so operators can spot recurring issues instead of only seeing the current reading's remark; (4) a "Save as PDF" option alongside the existing JPG export for the Infographic Report, for sites that need a PDF for formal record-keeping (uses jsPDF wrapping the same html2canvas raster already used for JPG).
- **"เลือกทั้งหมด" (Select All) + removal of the 10-item report cap.** Operators previously could select at most 10 parameters into the Infographic Report before hitting an alert; there was also no way to select everything in one click. The user confirmed they sometimes want to put the entire current filtered list into one report, so the cap was removed system-wide and a "Select All" button was added that selects everything currently visible under the active View/Time filter.
- **Clearing the database no longer wipes Tag definitions.** "ล้างฐานข้อมูล" (Clear Database) used to clear both `Records` (shift readings) and `Tags` (the Excel-derived tag/limit catalog), forcing a re-import just to get limits back in the Tags/Master tabs. It now only clears `Records`; `Tags` and `MasterTags` persist and get upserted on the next import. (Master overrides were never cleared by this button in the first place — that part was already correct.)
- **Per-tag "Force Standby" override.** Some equipment (e.g. `PM-401A` / `PM-401B`) sits idle for a shift, but its instruments (e.g. `VI-2401A`, a vibration sensor) don't read near true zero when idle — they show sensor baseline noise (e.g. ~13 against a norm of 20-100), which the existing near-zero "zero shield" heuristic doesn't catch. Rather than widen that heuristic globally (risking false negatives on genuinely abnormal readings elsewhere), a manual per-tag override (`master.forceStandby`) was added in the Master tab so an operator can flag a specific tag as Standby regardless of its value, until unflagged.
- **Removed the "Smart Shift Executive Summary" card from the Infographic Report.** This was a template-generated Thai paragraph summarizing the shift (via `SMART_AGENT.generateShiftSummary`, rule-based text, not a real AI call). The user asked to drop it from the report entirely; the dead code path was removed along with the UI.
